## Суть продукта

```
WISLA АРМ — модуль мониторинга рабочих станций (Windows и Linux) для службы технической поддержки. Лёгкий агент на каждом АРМ собирает метрики (CPU, RAM, диск), логи и критические события ОС и отправляет их на сервер. Оператор видит единый реестр станций, графики, журнал инцидентов и получает алерты в веб-интерфейсе, Telegram и на email при нарушении порогов (как в Zabbix-шаблонах). Прототип построен на форке платформы NetworckScaner с переиспользованием движка мониторинга, уведомлений и UI.
```

## Какие проблемы решает

```
• Нет единого реестра АРМ и актуального статуса «онлайн / недоступен»
• Ручной обход станций при жалобах пользователей — долгое время реакции (MTTR)
• Метрики и логи разрознены, нет истории для анализа
• Позднее обнаружение критических ситуаций (заполнение диска, перегруз CPU)
• Нет автоматических уведомлений оператору при срабатывании порогов
• Сложность масштабирования мониторинга без единого шаблона метрик и алертов
```

## Преимущества продукта

```
• Один агент (Go) на Windows и Linux — единый протокол и шаблоны метрик
• Переиспользование зрелого стека NetworckScaner: пороги, события, SMTP/Telegram, роли
• Шаблоны arm-linux / arm-windows — знакомая модель Zabbix для администраторов
• TimescaleDB — эффективное хранение истории метрик
• Веб-UI: реестр, карточка, события, настройки; мобильная вёрстка
• Быстрый пилот: 2 VM → масштаб до 5000 АРМ в roadmap
• Задел интеграции с центральной WISLA и LDAP/AD
```

## Выгоды для клиента от продукта (бизнес-часть)

```
• Сокращение времени обнаружения инцидентов на АРМ (проактивные алерты вместо звонков пользователей)
• Снижение простоя рабочих мест за счёт контроля диска, CPU и доступности агента
• Прозрачность для руководства: отчёт XLSX по парку АРМ и рекомендации
• Меньше нагрузки на ТП — один оператор видит весь парк в одном интерфейсе
• Снижение стоимости владения: не нужен отдельный Zabbix только для АРМ — модуль в экосистеме WISLA
• Быстрый MVP/пилот на 2–50 станций без больших внедренческих затрат
```

## Юзер-сценарии (3 штуки минимум)

```
Сценарий 1 — Оператор видит проблему до обращения пользователя
Дежурный инженер ТП получает в Telegram сообщение «Диск на pilot-linux-01 > 95%». Открывает WISLA АРМ → «События» → видит OPEN-инцидент, переходит в карточку станции, проверяет график диска и инициирует очистку. После нормализации метрики инцидент переходит в RESOLVED.

Сценарий 2 — Единый обзор парка АРМ
Администратор входит в систему, открывает реестр АРМ: pilot-linux-01 и pilot-windows-01 в статусе Online. Фильтрует по ОС, открывает карточку Windows-станции, смотрит CPU/RAM за сутки, убеждается в стабильной работе агента.

Сценарий 3 — Отчёт для руководства
Раз в неделю оператор скачивает отчёт XLSX «Парк АРМ»: лист с реестром и метриками, лист с рекомендациями (критический диск, offline, открытые инциденты). Передаёт файл руководителю ИТ для планирования обновлений и закупок дисков.
```
