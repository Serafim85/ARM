## 1. Архитектурное решение

### 1.1. Выбранный вариант

**Вариант A (рекомендованный):** форк платформы **NetworckScaner** с новыми модулями для АРМ, без переписывания движка мониторинга с нуля.

| Решение | Обоснование |
|---------|-------------|
| Монолит Spring Boot + Angular | Уже есть UI, роли, SMTP/Telegram, `.template` runtime, TimescaleDB |
| Отдельный **Go-агент** на АРМ | Лёгкий сбор метрик Win/Linux; контракт ingest не зависит от языка агента |
| **TimescaleDB** (PostgreSQL 16) | Hypertable для метрик; одна БД для событий и конфигурации |
| **Zabbix-шаблоны** `.template` | Заказчик ориентируется на Zabbix; пороги и ключи метрик — как в NS |
| **HTTPS batch JSON + API-key** | Согласовано в Excel V1; проще Kafka на агенте для MVP |

Подробные ADR: [`docs/DECISIONS.md`](DECISIONS.md) (ADR-001 … ADR-009).

### 1.2. Схема компонентов (MVP)

```
┌─────────────────┐     HTTPS POST          ┌──────────────────────────────┐
│ wisla-arm-agent │ ── /api/v1/agent/ingest ─►│ Spring Boot (wisla-arm)      │
│ Go · Win/Linux  │     X-Agent-Key           │ agentingest · workstation    │
└─────────────────┘                           │ monitoring · notifications   │
                                              └──────────────┬───────────────┘
                                                             │ JDBC
┌─────────────────┐     REST + JWT              ┌───────────▼──────────────┐
│ Angular UI      │ ◄──────────────────────────►│ TimescaleDB / PostgreSQL │
│ :3000           │                             │ БД wisla_arm :5435       │
└─────────────────┘                             └──────────────────────────┘

Внешние каналы: SMTP (email), Telegram Bot API, LDAP (демо OpenLDAP)
Отключено в MVP: Kafka, SNMP-сканер, topology, интеграция WISLA hub
```

Полные блок-схемы и sequence-диаграммы: [`docs/architecture/ARCHITECTURE-DIAGRAM.md`](architecture/ARCHITECTURE-DIAGRAM.md).

### 1.3. Поток данных (сквозной сценарий)

1. Агент каждые 30–60 с собирает CPU, RAM, диск, логи, события (BSoD).
2. `POST /api/v1/agent/ingest` → upsert `workstations`, запись `metric_values`, `log_events`.
3. `ArmWorkstationAlertService` → шаблон `arm-linux` / `arm-windows` → пороги → `monitoring_events`.
4. `NotificationDispatchService` → подписки SMTP / Telegram.
5. UI: реестр АРМ, карточка, графики, раздел **«События»**.

### 1.4. Что переиспользуем из NetworckScaner

| Модуль NS | Использование в WISLA АРМ |
|-----------|---------------------------|
| `monitoring` | `.template`, оценка порогов, `monitoring_events` |
| `notifications` | SMTP, Telegram, подписки |
| `users` | JWT, роли, LDAP-настройки |
| `frontend` | Angular, PrimeNG, дашборды (scan/topology скрыты) |
| Flyway + `metric_values` | Hypertable метрик |

### 1.5. Что отключено / не используется в АРМ

| Модуль NS | Причина |
|-----------|---------|
| `network.scan`, scanjobs | Не входит в scope мониторинга АРМ |
| SNMP collector | АРМ мониторится агентом, не SNMP |
| topology, Cisco inventory | Сетевой инвентарь не нужен для MVP АРМ |
| Kafka pipeline (MVP) | Ingest синхронный по HTTPS; Kafka — v2 / WISLA |

## 2. Стек технологий

| Слой | Технология | Версия / детали |
|------|------------|-----------------|
| **Агент** | Go | gopsutil; бинарник `wisla-arm-agent`; Linux + Windows |
| **Backend** | Java, Spring Boot | 3.4, profile `wisla-arm`, порт **8081** |
| **Frontend** | Angular, PrimeNG | 21, порт **3000** |
| **БД** | TimescaleDB / PostgreSQL | 16, порт host **5435**, БД `wisla_arm` |
| **Миграции** | Flyway | `backend/src/main/resources/db/migration/` |
| **Шаблоны** | Zabbix `.template` | `templates/arm-linux.template`, `arm-windows.template` |
| **Контейнеры** | Docker Compose | TimescaleDB; LDAP — опционально (`infra/docker-compose.ldap.yml`) |
| **Уведомления** | JavaMail, Telegram Bot API | Подписки OPERATOR, тег `arm-workstation` |
| **Auth** | JWT | LOCAL + LDAP (демо) |
| **Тесты** | JUnit, Playwright, smoke-скрипты | `tests/integration`, `tests/e2e`, `infra/smoke-stack.sh` |
| **Репозиторий** | GitHub | https://github.com/Serafim85/ARM |

**Язык агента:** Go на MVP (ADR-003). C возможен в v1/v2 при сохранении JSON-контракта ingest.

**Не выбрано:** InfluxDB, MongoDB, отдельный Zabbix-server, SQLite на сервере (SQLite — только как локальный буфер агента в roadmap).

## 3. Изначальные требования

### 3.1. Документы

| Документ | Назначение |
|----------|------------|
| `требования-мониторинг-АРМ.docx` | Полное ТЗ §1–§10 |

| `трекинг-требований.yaml` | 54 требования по ID (REQ-*) |

### 3.2. Целевой масштаб

- **v2:** до **5000** АРМ  
- **MVP (прототип):** **2 VM** (pilot-linux-01, pilot-windows-01)  
- **v1 (пилот):** 50–300 АРМ  

### 3.3. Осознанное ограничение scope MVP

По ADR-001 и согласованиям Excel V1 команда **2 человека**, срок прототипа **~3–4 недели** → в MVP входит **~45%** полного ТЗ. Остальное — v1/v2 или явный **waived**.

Критерии успеха MVP: [`docs/PHASES.md`](PHASES.md).

## 5. Что не реализовано и почему

### 5.1. Сознательно отложено (deferred) — фазы v1 / v2

| Тема | Требование / § | Почему не в MVP |
|------|----------------|---------------|
| **Интеграция WISLA** | §1.7 | Нет Swagger/API от команды WISLA; stub `WislaIntegrationPort` (ADR-007) |
| **Kafka** | §1.7, NS pipeline | Ingest по HTTPS достаточен для прототипа; Kafka — v2 server-side |
| **Политики агента с сервера** | §1.4.5 | Нужен Policy API + pull в агенте; v1 |
| **Прокси HTTP/HTTPS** | §1.5.6 | Excel: настройка через UI — v1 |
| **Полный pipeline логов** | §4.7–4.8 | MVP: warning/error в карточке; dedup, correlation, «обработано» — v1 |
| **Метрики по журналам** | §3.7 | MVP: сами логи; агрегированные счётчики — v1 |
| **Инвентарь железа, S/N** | §2.2 | Excel: не блокер MVP |
| **Профили мониторинга по группам** | §2.4 | Прототип: один шаблон на ОС (linux/windows) |
| **Ресурсы по службам** | §4.2–4.3 | v1 |
| **Полный аудит сессий** | §5 | MVP: last seen; вход/выход RDP/SSH — v1 |
| **PDF-отчёты** | §6 | v1/v2; XLSX есть |
| **SSO** | §8 | v1/v2 |
| **Горизонтальное масштабирование** | §1.6 | Архитектурные hooks; 5000 АРМ — v2 |
| **Tiered retention / агрегация** | §9.3 | v2; MVP: raw 30 дней |

### 5.2. Снято с scope (waived) — согласовано с заказчиком

| Тема | Требование / § | Причина waived |
|------|----------------|----------------|
| **Безагентный режим WinRM/SSH** | §1.9 | Excel V1: не нужен; мониторинг только через агент |
| **S.M.A.R.T. / здоровье диска** | §3.5 | Отдельное ПО; не входит в MVP АРМ |
| **Сканирование сети NS** | — | Другой продукт; в АРМ отключено |
| **SNMP-мониторинг** | — | АРМ — агент, не SNMP |
| **Security log audit (полный)** | §5 | v2 / отдельный контур |

### 5.3. Компромиссы прототипа (упрощения)

| Тема | Полное ТЗ | Что в MVP | Почему |
|------|-----------|-----------|--------|
| Ротация API-key «раз в час» | §1.5 | Статический dev-key + отзыв в UI | Упростить пилот; v1 — ротация |
| Логи | Полный SIEM | warning/error в карточке | 2 dev, 3 недели |
| Группы АРМ | Много тегов, профили | тег `arm-workstation`, шаблон по ОС | Достаточно для демо |
| Email Яндекс | SMTP | Настроено; пароль приложения с задержкой 2–3 ч | Ограничение Яндекса; live-демо — Telegram + UI |
| Окно техобслуживания | §7 | Базовая сущность NS | Полная логика mute — v1 |
