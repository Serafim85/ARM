## Продукт и задача

### Что такое WISLA АРМ?

**Ответ:** Модуль мониторинга рабочих станций Windows и Linux: единый реестр АРМ, метрики CPU/RAM/диск, события по порогам, алерты оператору в UI, email и Telegram. Сегодня — автономный прототип; в v2 — встраивание в центральную платформу WISLA.

**Если давят:** Целевой масштаб — до 5000 АРМ. Сейчас пилот на 2 VM, архитектура и контракт ingest рассчитаны на рост без смены протокола.

---

### Чем отличается от Zabbix / обычного мониторинга?

**Ответ:** Пороги и ключи метрик — в духе Zabbix (файлы `.template`), но продукт заточен под **АРМ в контуре WISLA**: свой агент, единый UI с ролями, задел интеграции с hub WISLA, отчёты по парку с рекомендациями.

**Если давят:** Мы не поднимаем отдельный Zabbix-server — переиспользуем движок шаблонов из форка NetworckScaner.

---

### Почему не весь ТЗ реализован?

**Ответ:** Полное ТЗ §1–§10 — это продукт на 5000 АРМ. По согласованной дорожной карте и Excel V1 прототип закрывает **~45%** — сквозной мониторинг на 2 VM. Остальное разбито на v1 (пилот 50–300 АРМ) и v2 (WISLA + масштаб).

**Если давят:** Есть матрица: что сделано, что deferred, что waived — документ в репозитории и на GitHub. Это не «недоделка», а **фиксированный scope MVP** для команды из двух человек за 3–4 недели.

---

### Закрыли ли обязательный функционал?

**Ответ:** **Обязательный функционал прототипа** — да по главному сценарию: агент → ingest → метрики → пороги → событие → UI + Telegram → отчёт XLSX. Полный docx целиком — нет, поэтапно до v2.

**Если давят:** Не закрыты в MVP по трекингу: мониторинг служб, журнал «обработано», окно ТО, буфер агента, полный аудит сессий — в ближайшем спринте v1.

## Архитектура

### Почему форк NetworckScaner, а не с нуля?

**Ответ:** В NS уже есть Spring Boot, Angular UI, движок `.template`, события, SMTP/Telegram, TimescaleDB, LDAP. Переписывать это за 3 недели — риск без ценности. Мы добавили модули **agent-ingest** и **workstation**, отключили scan/SNMP/topology.

**Если давят:** ADR-002 в `DECISIONS.md`. Ingest вынесен за интерфейс `AgentIngestPort` — при росте можно вынести в worker без смены агента.

---

### Как устроен поток данных?

**Ответ:** Go-агент на АРМ каждые 30–60 с шлёт batch JSON на `POST /api/v1/agent/ingest` с API-key. Backend пишет метрики в TimescaleDB, оценивает пороги из `arm-linux` / `arm-windows`, создаёт `monitoring_events`, шлёт уведомления. UI читает REST API.

**Если давят:** Sequence-диаграммы — `docs/architecture/ARCHITECTURE-DIAGRAM.md`.

---

### Почему монолит, а не микросервисы?

**Ответ:** Для MVP и пилота 50–300 АРМ монолит Spring Boot проще развёртывать и отлаживать. Точки расширения уже есть: ingest port, WISLA port, отдельные модули в одном приложении.

**Если давят:** Горизонтальное масштабирование и read-replica — v2; на демо показываем корректную декомпозицию логики, не обязательно физические микросервисы.

---

### Почему TimescaleDB, а не InfluxDB / VictoriaMetrics?

**Ответ:** NS и метрики уже на PostgreSQL + hypertable `metric_values`. Одна СУБД для метрик, событий и конфигурации — меньше операционной сложности для команды и заказчика.

**Если давят:** Tiered retention (raw → hourly → daily) — v2 через continuous aggregates TimescaleDB.

---

## Агент

### Почему Go, а не C из приложения к архитектуре?

**Ответ:** Один код на Linux и Windows, быстрая разработка, gopsutil для метрик, маленький бинарник. **Контракт ingest — JSON по HTTPS** — backend не зависит от языка агента.

**Если давят:** C остаётся опцией v1/v2: замена бинарника при тех же ключах метрик в `.template`, без переписывания сервера. ADR-003.

---

### Почему агент не как Windows Service / systemd на демо?

**Ответ:** На пилотных VM агент запускается в dev-режиме для отладки. Упаковка в службу ОС — deliverable v1 (MSI/deb/rpm), логика сбора та же.

**Если давят:** Для production пилота — systemd unit и Windows Service wrapper; это инсталляция, не смена архитектуры.

---

### Почему нет локального буфера при offline сервера?

**Ответ:** В MVP приоритет — стабильный online-сценарий и ingest. Буфер на SQLite на АРМ — в roadmap (§1.4.11), реализуется вместе с policy API в v1.

**Если давят:** Архитектурно не блокер: агент копит batch локально и догружает после восстановления связи.

---

### Почему HTTPS, а не Kafka на агенте?

**Ответ:** Kafka на каждом АРМ — лишняя зависимость и операционка. Batch HTTPS с API-key согласован в Excel V1 и проще для файрволов заказчика.

**Если давят:** Kafka для **интеграции с hub WISLA** — server-side в v2; агент по-прежнему может слать HTTPS на наш backend.

---

### Как защищён канал агента?

**Ответ:** HTTPS, API-key в заголовке `X-Agent-Key`, ключ хранится как hash в БД, отзыв через UI. На v1 — ротация ключей и опционально mTLS без смены JSON-схемы.

**Если давят:** JWT — для пользователей UI, не для агентов; это разные контуры аутентификации.

---

## Интеграции и блокеры

### Где интеграция с центральной WISLA?

**Ответ:** В roadmap **v2**. В коде — `WislaIntegrationPort` и заглушка `NoOpWislaIntegration`. Референс-контракты есть в vendor NS (`INTEGRATION_WISLA_*.md`).

**Если давят:** **Архитектурный блокер:** нет production Swagger/API от команды WISLA — без интеграционного стенда hub нельзя честно показать live. Прототип АРМ автономен и не блокируется внешним API.

---

### Почему нет SSO?

**Ответ:** SSO через WISLA — waived для пилота (Excel V1). В MVP — локальный вход и задел LDAP. OIDC-hook заложен в auth-модуле NS на v2.

**Если давят:** На стенде заказчика подключаем их IdP; без их OIDC endpoints live SSO на демо бессмысленен.

---

### Почему LDAP не показываете live?

**Ответ:** UI и настройки LDAP/AD есть; на демо — **локальный вход**. Live AD требует каталог заказчика: DC, bind, группы, сертификаты — это интеграционный стенд, не ноутбук разработчика.

**Если давят:** OpenLDAP в docker-compose — для разработки; production — `demo-setup-ldap.sh` и маппинг групп в роли ADMIN/OPERATOR.

---

### Почему email может не прийти на демо?

**Ответ:** SMTP настроен (Yandex); для приложений Яндекса нужен **пароль приложения** с задержкой активации 2–3 часа. На защите опираемся на **Telegram и UI** — они не зависят от почтового контура заказчика.

**Если давят:** В контуре заказчика — свой relay; наш код использует стандартный JavaMail + подписки OPERATOR.

---

## Функционал ТЗ

### Почему нет мониторинга служб?

**Ответ:** В MVP закрыты метрики хоста, диск, offline, BSoD, логи. Контроль перечня служб (§4.1) — следующий спринт: список в конфиге агента + items в `.template`.

**Если давят:** В Excel V1 для прототипа акцент на **общее состояние хоста**, не CPU по каждой службе — ресурсы по службам в v1.

---

### Почему нет S.M.A.R.T.?

**Ответ:** **Waived** по согласованию с заказчиком — отдельное ПО и права на диски; не блокер MVP мониторинга АРМ.

---

### Почему нет безагентного режима WinRM/SSH?

**Ответ:** **Waived** в Excel V1 — мониторинг только через агент. Безагентный режим усложняет безопасность и не даёт единого качества телеметрии.

---

### Почему один диск, а не все тома?

**Ответ:** MVP — системный том `/` или `C:`. Несколько разделов (§10.3) — v1: discovery в агенте + items в шаблоне.

---

### Где полный аудит сессий (вход/выход, RDP)?

**Ответ:** MVP — last seen и best effort текущий пользователь. Полный §5 (RDP/SSH, session_events) — v1; Security log глубокий — waived / v2.

**Если давят:** На Windows нужен доступ к Security log и политики аудита на стенде заказчика.

---

### Где PDF-отчёты?

**Ответ:** В MVP по Excel V1 обязательны **CSV и XLSX** — оба есть. PDF — «если успеем»; XLSX с листом рекомендаций уже закрывает потребность руководства на пилоте.

---

### Что такое отчёт с рекомендациями?

**Ответ:** `GET /api/v1/workstations/export.xlsx` — два листа: реестр АРМ и **авто-рекомендации** по offline, диску >95%, открытым инцидентам, BSoD. Правила — из сработавших триггеров и статусов.

---

### Почему события в меню «События», а не только в карточке?

**Ответ:** **Меню «События»** — лента `monitoring_events` по парку (алерты OPEN/RESOLVED). **Карточка АРМ** — BSoD и логи warning/error с этого хоста. Разные сущности, оба требования §4.

---

## Масштаб и надёжность

### Выдержит ли 5000 АРМ?

**Ответ:** Архитектурно — да при batch ingest, TimescaleDB, tiered storage в v2. Прототип проверен на 2 VM; нагрузочный пилот 50–300 — v1 на инфраструктуре заказчика.

**Если давят:** Узкое место — не агент (лёгкий), а запись в БД и оценка порогов; для v2 — агрегация, retention policies, при необходимости вынос ingest worker.

---

### Какие тесты есть?

**Ответ:** Пирамида: unit (Go, JUnit, Angular), integration (ingest → DB), E2E Playwright (login, список, карточка), smoke `./infra/smoke-stack.sh`.

**Если давят:** Матрица покрытия — `docs/TEST-COVERAGE.md`. Soak 3+ дня на 2 VM — чеклист пилота.

---

### Что если демо упадёт?

**Ответ:** Есть smoke-скрипты, повторяемый `demo-fire-alert.sh`, скриншоты и документация на GitHub. Код и архитектура не зависят от одного live-прогона.

## UX, AI, процесс

### Почему UI «как корпоративный шаблон»?

**Ответ:** PrimeNG + форк NS — зрелый UI для enterprise. Для MVP важнее логика ТП: реестр, карточка, события, экспорт. Уникальный дизайн — после валидации сценариев с заказчиком.

---

### Как использовали AI?

**Ответ:** **Cursor** — ускорение boilerplate, тестов, infra-скриптов, документации, ревью. **Команда** — архитектура, scope MVP, согласования с ТЗ, приёмочные сценарии, финальная ответственность за код.

**Если давят:** ADR-008, `AGENTS.md`, `.cursor/rules/` — процесс задокументирован; секреты в git не коммитим.

---

### Почему репозиторий на GitHub?

**Ответ:** Прозрачность для жюри и заказчика: код, docs, диаграммы, ADR, скрипты демо — https://github.com/Serafim85/ARM

## Roadmap

### Что в v1 после прототипа?

**Ответ:** 50–300 АРМ, policy с сервера, полный log pipeline, аудит сессий, службы, настраиваемый retention, LDAP production, обновление агента MSI/deb.

---

### Что в v2?

**Ответ:** Интеграция WISLA (Kafka + REST), SSO, tiered metrics, горизонтальное масштабирование, закрытие оставшихся пунктов ТЗ кроме waived.

| Вопрос | Ответ одной фразой |
|--------|-------------------|
| «Это же просто форк, вы ничего не сделали» | Форк — осознанный ADR; greenfield агент, ingest API, шаблоны АРМ, реестр, сквозные алерты — наше |
