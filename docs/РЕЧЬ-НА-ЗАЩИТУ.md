## Полная версия

Добрый день.

Мы представляем **WISLA АРМ** — модуль мониторинга рабочих станций для инфраструктуры WISLA.

**Задача простая и знакомая любой техподдержке:** в организации сотни и тысячи компьютеров — Windows и Linux — и инженеру нужно в одном месте видеть: какие АРМ живы, что с ресурсами, где заканчивается диск, был ли сбой, кому и как быстро сообщить. Сейчас это часто разрозненные инструменты. Мы делаем **единый реестр АРМ** с метриками, событиями и оповещениями — в духе привычного Zabbix, но как часть экосистемы WISLA.

Сегодня показываем **рабочий прототип** — не презентацию на слайдах, а **сквозной сценарий на двух виртуальных машинах**: Linux и Windows. Агент собирает данные, сервер принимает и хранит, интерфейс показывает, пороги срабатывают, оператор получает уведомление.

---

**На что мы ориентировались при проектировании.**

Первый ориентир — **техническое задание** на мониторинг АРМ: метрики, события, алерты, интерфейс, хранение. Второй — **согласования с заказчиком** в Excel: что обязательно в первой версии, что можно отложить. Третий — **практика эксплуатации**: заказчик привык к **Zabbix-шаблонам** — пороги CPU, диска, триггеры. Мы не изобретали свой язык правил, а используем **файлы `.template`** — те же ключи метрик, что и в Zabbix.

Честно: полное ТЗ на все пять тысяч АРМ — это не один спринт. Команда — **два человека**, срок прототипа — **три–четыре недели**. Мы зафиксировали scope **MVP**: агент, приём данных, реестр, карточка, графики, алерты, логи, BSoD. Остальное — **дорожная карта v1 и v2** с явными обоснованиями. Это не «не успели», а **согласованное разбиение** — иначе не было бы стабильного демо.

---

**Почему такая архитектура.**

Мы выбрали **вариант A**: не писать платформу мониторинга с нуля, а **развить форк NetworckScaner** — там уже есть Spring Boot backend, Angular UI, движок `.template`, события, SMTP, Telegram, TimescaleDB, роли пользователей. Наша работа — **новые модули под АРМ**: ingest агента, реестр `workstations`, шаблоны `arm-linux` и `arm-windows`. Сетевой SNMP-сканер и топологию **отключили** — они не про мониторинг рабочих станций.

**Агент — отдельный лёгкий процесс на каждом АРМ.** Язык — **Go**.

Почему Go, а не C, как в приложении к архитектуре?

- **Один код** на Linux и Windows — один бинарник, кросс-компиляция.
- Библиотека **gopsutil** — CPU, память, диск без тяжёлой нативной обвязки.
- Для прототипа на двух VM это **быстрее и безопаснее** для маленькой команды.
- Главное: **контракт передачи данных** — JSON batch по HTTPS с API-key — **не зависит от языка**. Backend и UI не знают, на чём написан агент. В v1/v2 агент можно заменить на C **без переписывания сервера** — drop-in бинарник с теми же ключами метрик.

**Транспорт — HTTPS, не Kafka на агенте.** Агент раз в 30–60 секунд шлёт пакет: метрики, логи, события. Сервер по ключу **автоматически регистрирует** АРМ при первом успешном запросе. Kafka в roadmap — **на стороне сервера**, когда появится интеграция с центральной WISLA. На MVP синхронный ingest проще, надёжнее и достаточен для тысяч агентов при нормальном batch.

**База — TimescaleDB на PostgreSQL 16.** Метрики — во временных рядах, hypertable; события и конфигурация — в той же БД. Одна СУБД проще сопровождать, чем связка InfluxDB + отдельное хранилище.

---

**Как это работает — один цикл.**

1. На АРМ работает **wisla-arm-agent** — собирает CPU, RAM, заполнение системного диска, warning/error из журнала, при необходимости BSoD.
2. **POST** на `/api/v1/agent/ingest` с заголовком **X-Agent-Key**.
3. Backend обновляет реестр, пишет метрики в TimescaleDB, логи и события — в свои таблицы.
4. **Движок шаблонов** сравнивает метрики с порогами из `arm-linux` / `arm-windows` — как в Zabbix.
5. При превышении — **monitoring event** со статусом OPEN; при нормализации — RESOLVED.
6. **Notification service** шлёт в Telegram и на email по подпискам оператора.
7. Инженер открывает **веб-интерфейс**: реестр АРМ, карточка с графиками, раздел **«События»** — вся лента инцидентов по парку.

Сегодня это можно пройти **от начала до конца** на живом стенде.

---

**Что сознательно не в прототипе — и почему.**

Не потому что «не важно», а потому что **без инфраструктуры заказчика или внешних API это архитектурные блокеры**, а не недоделка за три недели.

**Интеграция с центральным hub WISLA.** В ТЗ и в NetworckScaner есть Kafka-мост и контракты событий. Но **Swagger и production API от команды WISLA мы не получили** — в Excel зафиксировано: интеграция не блокирует первую версию. В коде — интерфейс `WislaIntegrationPort` и заглушка. На интеграционном стенде WISLA подключим реальную реализацию — **контракт уже заложен**.

**Полноценный вход через Active Directory заказчика.** UI и настройки LDAP есть, на демо — локальный вход. **Привязка к реальному AD** — только на стенде заказчика: сервер, bind, группы, сертификаты. Без этого live LDAP на защите — лотерея.

**SSO через WISLA** — то же: нужен OIDC-провайдер центральной платформы.

**Корпоративный SMTP** — настройки есть, Yandex для демо. В контуре заказчика — свой relay, политики, белые списки. На демо опираемся на **Telegram и UI** — они не зависят от почтового контура.

**Политики агента с сервера** — в v1: нужен Policy API и периодический pull на каждом АРМ. В прототипе конфиг локальный — осознанно, чтобы не усложнять пилот.

**Мониторинг на парке 50–300 и 5000 АРМ** — архитектура к масштабу готова, но **soak-тест на сотнях машин** — этап пилота на инфраструктуре заказчика, не на двух VM разработчика.

**S.M.A.R.T., безагентный WinRM/SSH, полный Security log** — по согласованию с заказчиком **сняты с scope** MVP: отдельное ПО или другой контур безопасности.

Всё это — в документе **«Архитектура, стек и требования»** и в журнале решений ADR: что сделано, что отложено, что waived — **прозрачно для приёмки**.

---

**Что сверх минимального MVP.**

Уже есть **отчёт XLSX по парку** с листом **автоматических рекомендаций** — диск, offline, открытые инциденты. Это задел v1, но работает сейчас. Есть smoke-автоматизация, диаграммы архитектуры, репозиторий на GitHub.

## Короткая версия (~2 мин)

Добрый день. **WISLA АРМ** — мониторинг рабочих станций Windows и Linux в экосистеме WISLA: единый реестр, метрики CPU/RAM/диск, события по порогам как в Zabbix, алерты в UI, email и Telegram.

Мы показываем **рабочий прототип**, не макет: два АРМ — Linux и Windows — реальные агенты, реальная база, реальные алерты.

**Архитектура:** форк платформы NetworckScaner — backend, UI, шаблоны, уведомления уже были; мы добавили **Go-агент** и **ingest API**. Go выбрали для быстрого кросс-платформенного MVP; протокол JSON по HTTPS **не привязан к языку** — агент можно заменить без переделки сервера. Данные — в **TimescaleDB**, пороги — из **Zabbix-шаблонов** `.template`.

**Не в прототипе осознанно:** интеграция с hub WISLA — нет внешнего API; полный AD/SSO — нужен стенд заказчика; Kafka на агенте не нужен — ingest по HTTPS. Заглушки и ADR в репозитории, подключение на интеграционном контуре.

Сейчас — **live**: реестр → карточка → авария по диску → Telegram → отчёт XLSX.
